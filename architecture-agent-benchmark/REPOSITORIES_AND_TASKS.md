# Репозитории и задачи

Этот документ описывает все 10 репозиториев и все 40 задач бенчмарка простым языком — для тех,
кто хочет понять суть эксперимента без чтения `PROTOCOL.md`/`repos.yaml`/`tasks/` напрямую.

Источник: `repos.yaml` (профиль каждого репозитория) и реальные промпты `tasks/R0X/task_[A-D].md`
(ровно то, что видел AI-агент). Здесь **не** используются `tasks/R0X/metadata_*.yaml` — это
отдельные файлы с эталонным решением и критериями оценки (см. `PROTOCOL.md` §9); они есть в этом
репозитории для полной воспроизводимости, но не пересказываются здесь, чтобы не путать "что
просили сделать" с "как это должно было быть сделано правильно".

## Четыре типа задач (одинаковые для каждого репозитория)

- **A — Local Change**: ограниченное изменение одного компонента.
- **B — Cross-Module Feature**: фича, реально затрагивающая ≥2 (как правило ≥3) архитектурные границы.
- **C — Existing Extension Point**: в репозитории уже есть спроектированный механизм расширения
  (интерфейс/плагин/provider/registry/factory/strategy/adapter/middleware) — промпт не называет
  его напрямую, агент должен сам его найти или не найти.
- **D — Architecture Trap**: у задачи есть "лёгкое" решение, которое компилируется и проходит
  функциональные тесты, но нарушает архитектуру, и "правильное" решение, требующее понимания
  существующих границ.

---

## R01 — freqtrade/freqtrade

Python, ~44.8k строк production-кода, 325 файлов. Модульный монолит + плагинный слой (`exchange`,
`strategy`, `optimize`, `plugins/pairlist`, `plugins/protections`, `resolvers`, `rpc`, `freqai`).
Модульность кода сильная, но архитектурная документация практически отсутствует (нет
ARCHITECTURE.md/AGENTS.md, только частичный `docs/developer.md`) — выбран как профиль "код
хорошо структурирован, но ничего про это не написано".

- **A:** добавить проверку конфликта конфигурации при старте — если пользователь одновременно
  задал фиксированную сумму капитала и процент от баланса, они тихо конфликтуют (срабатывает
  только один параметр); проверка должна срабатывать на той же фазе, что и другие проверки
  противоречивой конфигурации.
- **B:** добавить настраиваемый лимит суммарной капитальной экспозиции по валюте маржи (например,
  несколько BTC-маржинальных позиций одновременно); новые сделки, превышающие лимит, должны
  пропускаться/урезаться; поведение должно быть идентичным в live/dry-run и в backtest.
- **C:** добавить кулдаун после серии убыточных сделок — трекинг последовательных убытков по паре
  (и по боту целиком), пауза новых входов на настраиваемый период, видимость через существующий
  канал уведомлений об авто-паузе.
- **D (ловушка):** добавить короткоживущий кэш для запросов текущей цены в live/dry-run трейдинге
  (та же пара иногда запрашивается несколько раз за секунды, упираясь в rate limit биржи); не
  должен трогать backtest/hyperopt, не должен менять поведение при промахе кэша.

## R02 — saltstack/salt

Python, ~275.5k строк, 949 файлов. Плагинная архитектура на loader'е (`modules`, `states`,
`runners`, `grains`, `beacons`, `engines`, `returners` и ~17 других loader-управляемых категорий).
Модульность средняя (плоские `salt/modules/`, `salt/utils/` со связностью через неявную
dunder-конвенцию `__salt__[...]`). Выбран как самый большой пример "органической", не идеально
чистой модульности.

- **A:** добавить в существующий beacon disk-usage новый режим алерта — "использование упало ниже
  ожидаемого" (симптом незамонтированного диска), рядом с уже существующим алертом "использование
  выросло выше порога".
- **B:** добавить CLI-команду, показывающую, когда каждый beacon миньона последний раз
  срабатывал и была ли ошибка — живьём, без ожидания нового цикла опроса и без чтения логов.
- **C:** добавить опциональный SQLite-backend для кэша мастера (снимки grains, mine-данные,
  job-результаты) — альтернатива Redis/MySQL для single-node установок, только стандартная
  библиотека Python.
- **D (ловушка):** сделать повторные вызовы команды disk-usage (сейчас каждый раз вызывает `df`)
  быстрыми при повторных вызовах с одинаковыми аргументами в рамках одного запуска Salt, без
  изменения сигнатуры и без устаревания данных между отдельными запусками.

## R03 — nestjs/nest

TypeScript, ~34.7k строк, 621 файл. Слоистая DI-архитектура с адаптерами (`packages/core`,
`common`, `microservices`, `platform-express/fastify/ws/socket.io`, `testing`, `websockets`),
строгое направление зависимостей core/common←adapter. Модульность сильная — эталонный случай для
проверки "правильного направления зависимостей".

- **A:** добавить отсутствующий класс-исключение `429 Too Many Requests`, строго по конвенции
  одного класса на HTTP-статус (конструктор, дефолтное сообщение, возможность override,
  документация/тесты), как у соседних `BadRequestException`, `ConflictException` и т.д.
- **B:** добавить уведомление WebSocket-клиентов перед graceful shutdown — при получении
  Kubernetes-сигнала завершения подключённые клиенты должны получить короткое сообщение "сервер
  уходит" непосредственно перед разрывом соединения; должно одинаково работать для socket.io и
  `ws`, безопасно по умолчанию для шлюзов без клиентов.
- **C:** добавить "режим обслуживания" — возможность помечать отдельные route-хендлеры или целые
  контроллеры; при включении (переключаемом в runtime, не через редеплой) вызовы к помеченным
  хендлерам отклоняются до выполнения их логики; единый механизм для HTTP и WebSocket хендлеров,
  тестируемый без реального сервера/сокета.
- **D (ловушка):** добавить уникальный correlation-id заголовок на каждый HTTP-ответ (повторно
  использующий входящий ID, если клиент его уже прислал), доступный коду приложения (например,
  для логирования) без повторного парсинга из ответа; должен одинаково работать на обоих
  HTTP-адаптерах фреймворка (Express и Fastify).

## R04 — excalidraw/excalidraw

TypeScript, ~106.5k строк, 479 файлов. Пакетный монорепозиторий (`packages/excalidraw`,
`element`, `math`, `common`, `utils`, `fractional-indexing`, `laser-pointer`, `excalidraw-app`) с
явным реестром действий (`actions/manager.tsx`). Модульность сильная — сильный кандидат для
задачи C, архитектурно непохожий на NestJS несмотря на тот же язык.

- **A:** сделать переименование рисунка устойчивым к недопустимым для файловой системы символам
  (`/ \ : * ? " < > |`, пустым/пробельным именам, завершающим точкам/пробелам) так, чтобы
  итоговое имя файла при сохранении/экспорте было валидным на Windows/macOS/Linux, с видимой
  пользователю корректировкой.
- **B:** добавить живой показ площади фигуры в панели статистики выделения (сейчас там только
  ширина/высота) — корректно для прямоугольников, ромбов, эллипсов и любых замкнутых/заполненных
  контуров (включая рисованные от руки), корректно при повороте, не показывается для фигур без
  значимой площади (открытые линии, текст).
- **C:** добавить мгновенный недеструктивный тоггл показать/скрыть все текстовые подписи,
  привязанные к фигурам, во всём рисунке — доступный из тех же мест, что другие глобальные
  тоглы отображения (меню + горячая клавиша), с видимым состоянием вкл/выкл.
- **D (ловушка):** добавить команду "примагнитить к сетке" в один клик — привязывает
  позицию/размер выделенных фигур (или всех, если ничего не выделено) к настроенной сетке рисунка
  за один шаг, отменяемую одним шагом Undo, корректно синхронизируемую для соавторов.

## R05 — VictoriaMetrics/VictoriaMetrics

Go, ~120.1k строк, 643 файла. Плагинный паттерн (`lib/promscrape/discovery`, 22 backend'а service
discovery) соседствует с "god package" `lib/storage` (30.8k строк в 34 файлах в одном месте) —
специально выбран, чтобы в одном кодбейзе была и чистая, и "грязная" подсистема.

- **A:** добавить relabel-действие "обрезать пробелы" у значения лейбла, настраиваемое через
  source/target лейблы так же, как существующие преобразующие значение действия (uppercase/
  lowercase), для scrape-time и remote-write relabeling.
- **B:** добавить настраиваемый максимум активных scrape-таргетов на один job (`job_name`),
  независимо от того, какой discovery-механизм их породил; таргеты сверх лимита должны
  урезаться (не крашить и не оставаться безлимитными), с видимостью через существующий интерфейс
  статуса scrape-таргетов.
- **C:** добавить автоматическое обнаружение scrape-таргетов для Scaleway Instances (европейский
  облачный провайдер), следуя существующим конвенциям именования, интервала обновления,
  обработки ошибок и лейблинга — так же, как уже реализованные интеграции с другими
  облачными провайдерами/оркестраторами.
- **D (ловушка):** добавить учёт дропнутых сэмплов по имени метрики при превышении лимитов
  `-storage.maxHourlySeries`/`-storage.maxDailySeries`, с возможностью запроса топ-N
  "виновных" имён метрик, с жёстким ограничением памяти (чтобы инсталляции с миллионами
  уникальных имён метрик не взорвали память), нулевой overhead при выключенной фиче.

## R06 — etcd-io/etcd

Go, ~62.3k строк, 585 файлов в 13-модульном go.work воркспейсе (`api/`, `server/`, `client/v3`,
`etcdctl`, `pkg/`). Модульный монолит, Raft-based KV-хранилище под Kubernetes, чистая
Storage/Backend абстракция. Выбран как "чистый" Go-бейзлайн без заранее подготовленных
AI-инструкций в репозитории.

- **A:** запретить пустые/бланковые пароли при создании пользователя и смене пароля, кроме
  аккаунтов, явно включивших режим без пароля — с отдельной явной клиентской ошибкой (не путать
  с "пользователь не найден"/"уже существует").
- **B:** добавить настраиваемый лимит числа ключей, которые можно прикрепить к одному lease
  (с безопасным дефолтом, переопределяемым при старте сервера) — отклонение записи сверх лимита
  чистой клиентской ошибкой, без краша/зависания/частичного применения/порчи данных.
- **C:** добавить единый аудит-лог всех KV-запросов (чтение/запись/удаление/транзакция) — личность
  вызывающего (или "unauthenticated"), тип операции, ключ/диапазон, длительность, результат —
  применяемый ко всем типам запросов без ручной инструментации каждого хендлера.
- **D (ловушка):** добавить кэширование повторных идентичных запросов на чтение, инвалидация
  привязана к реальному изменению данных (не фиксированный TTL, который мог бы отдать устаревшие
  данные во время параллельной записи) — результат не должен быть "более устаревшим", чем
  обычное некэшированное чтение, ни при linearizable, ни при serializable консистентности.

## R07 — mihonapp/mihon

Kotlin, ~77.4k строк, 896 файлов, 14 Gradle-модулей со слоями domain/data/presentation, плюс
`source-api` provider/factory extension system. Модульность сильная — учебниковый
provider/factory extension point, специально спроектированный для сторонних расширений; слабое
место — тонкое тестовое покрытие (всего 7 unit-тестовых файлов).

- **A:** сделать так, чтобы добавление произвольного URL репозитория расширений сразу отклоняло
  очевидно невалидный ввод (пустой, не http(s), некорректный текст) понятной ошибкой, до любого
  сетевого запроса — сейчас невалидный ввод падает глубоко с непонятной сетевой ошибкой.
- **B:** добавить "напомнить позже" для ленты обновлений — временно скрыть конкретную серию из
  ленты на выбранный срок (из списка обновлений или со страницы деталей серии); главы продолжают
  скачиваться в фоне; серия появляется снова автоматически по истечении срока или вручную;
  должно корректно работать с существующими фильтрами ленты (прочитано/непрочитано, категория,
  закладки).
- **C:** добавить поддержку синхронизации прогресса чтения с self-hosted сервером манги/комиксов
  (в том же духе, что уже существующие похожие интеграции) — логин, непрерывная синхронизация
  прогресса по мере чтения, вид того, какие записи библиотеки сейчас привязаны.
- **D (ловушка):** добавить кэширование повторных поисков/листингов источника (тот же
  запрос+фильтры вскоре после предыдущего идентичного поиска, плюс "популярное"/"новое"), чтобы
  результаты приходили из кэша; кэш должен истекать через разумное время и поддерживать форс-
  рефреш (pull-to-refresh); постраничная подгрузка кэшированных результатов должна продолжать
  работать.

## R08 — signalapp/Signal-Android

Kotlin (371.9k строк измерено; плюс 175.1k легаси Java), 3337 файлов, 49 Gradle-модулей
(`feature/*`, `lib/*`, `core`) плюс `jobmanager/` и 116 файлов `*Repository.kt`. Модульность
сильная. Единственный подходящий очень крупный Kotlin-кандидат, не отмеченный как потенциально
загрязнённый AI-инструментарием; делит организацию/лицензию (AGPL-3.0) с R10 — задокументированная
угроза валидности, не исправлялась.

- **A:** отсортировать экран "Заблокированные контакты" по алфавиту (регистронезависимо) по
  отображаемому имени, как уже делают большинство других списков контактов в приложении; список
  должен оставаться корректно отсортированным при живом изменении (блокировка/разблокировка) во
  время просмотра экрана.
- **B:** позволить отметить один вложенный файл в batch-отправке как "в полном качестве",
  переопределяя дефолтное сжатие пачки только для этого файла — должно сработать даже если
  загрузка этого файла уже началась в фоне, и выбор должен сохраниться при убийстве/перезапуске
  приложения во время отправки.
- **C:** добавить периодическую фоновую рутину, находящую и удаляющую осиротевшие файлы
  thumbnail-кэша (больше не соответствующие никакому существующему вложению/сообщению); должна
  запускаться по регулярному расписанию (не только один раз после обновления), оставаться
  низкоприоритетной, не запускаться во время активного звонка или при критически низком заряде,
  и разумно возобновляться (не с нуля и не зависая) при прерывании посреди большого сканирования.
- **D (ловушка):** добавить кэширование повторных идентичных поисков по списку чатов (тот же
  текст/фильтры), чтобы повторный поиск был заметно быстрее, при этом новые/изменённые/удалённые
  сообщения, затрагивающие ранее закэшированный запрос, должны отражаться при следующем
  идентичном поиске (без устаревания); разные поисковые запросы кэшируются независимо.

## R09 — mozilla-mobile/firefox-ios

Swift, ~245.2k строк, 2047 файлов; пакет `BrowserKit` на SwiftPM (~20 независимых библиотечных
таргетов) плюс основное приложение Client (Focus-браузер вне зоны эксперимента). Component +
Redux-подобная unidirectional-dataflow архитектура (Reducer/Action/Middleware/Store).
Лучше всего задокументированный репозиторий из всех десяти (AGENTS.md, CLAUDE.md,
CONTRIBUTING.md, настоящие ADR) — сильная контрольная точка для вопроса "а может, явная
проза-документация уже решает проблему архитектуры?". Известное ограничение: полный тест-сьют
основного приложения зависит от приватного Bitrise CI Mozilla, поэтому задачи B и D проверяются
вручную, а не автоматическими тестами (только A и C реально гоняются через `swift test` внутри
BrowserKit).

- **A:** починить осиротевшие backup-файлы — при удалении сохранённых данных окна (вкладки/сессия)
  должна удаляться и основная копия, и её резервная копия восстановления (сейчас удаляется только
  основная, оставляя растущую кучу устаревших backup-файлов).
- **B:** добавить третью опцию "Закрыть вкладку" для настраиваемой средней кнопки навигационного
  тулбара, рядом с существующими "Home" и "New Tab" — там же, где делается текущий выбор, с тем
  же сохранением настройки, с той же аналитикой нажатий.
- **C:** A/B-тест альтернативного speech-to-text пайплайна для голосового поиска за простым
  флагом — у зачисленных в тест пользователей альтернативный пайплайн, у остальных дефолтный, с
  нулевой видимой разницей в поведении (кнопка записи, промежуточные результаты стриминга,
  обработка ошибок, отмена) независимо от пайплайна.
- **D (ловушка):** добавить короткий тост-подтверждение после существующего действия "Copy
  Address" (копирует URL текущей страницы в буфер обмена) — сейчас копирование происходит молча;
  должно появляться сразу после копирования и само закрываться.

## R10 — signalapp/Signal-iOS

Swift, ~548.0k строк, 2270 файлов (`SignalServiceKit`, `SignalUI`, плюс расширения приложения
share/notification-service). Component + layered архитектура с несколькими крупными
фреймворками. Крупнейший проверенный Swift-кандидат, с чистой точкой расширения
JobRunner/JobRunnerFactory; собирается только из публичных прекомпилированных бинарников и
CocoaPods (без приватной инфраструктуры). Делит организацию/лицензию (AGPL-3.0) с R08 —
задокументированная угроза валидности.
