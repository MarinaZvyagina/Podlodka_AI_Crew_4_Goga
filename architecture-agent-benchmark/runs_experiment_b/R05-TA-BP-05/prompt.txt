## Ticket: Support trimming whitespace from label values during relabeling

Several users have reported that after certain `relabel_configs` rules run — for example
when a label value is copied from a source that adds a trailing newline, or when several
source label values are concatenated together — the resulting label value ends up with
leading or trailing whitespace. Downstream systems (dashboards, alerting rules, exact-match
label filters) then fail to match these labels because of the stray whitespace, and the only
current workaround is a fragile regex-based `replace` rule that users have to hand-craft and
frequently get wrong.

Please add a way to strip leading and trailing whitespace from a label value as part of the
relabeling process, so it can be used the same way people already use relabeling to change the
case of a label value or copy one label into another. It should work for both scrape-time
relabeling (`relabel_configs`) and remote-write relabeling, since these share the same
configuration format.

Requirements:

- Users can configure a relabeling rule that takes one or more source labels, and stores the
  whitespace-trimmed value into a target label — mirroring how existing rules that transform a
  label value (rather than filter or drop targets) are configured (i.e. via source label(s) and
  a target label).
- If the rule is misconfigured (e.g. no destination label given), config loading should fail
  with a clear, actionable error message, consistent with how other misconfigured relabeling
  rules are already rejected today.
- All existing relabeling behavior must remain unchanged.
- Add a short entry to the relabeling documentation describing the new capability, and cover it
  with a unit test.

This should be a small, self-contained change — no new configuration file formats, no new
services, and no changes to how scrape targets are discovered.


This repository has Goga tooling and skills available (already connected) if you find them useful for this task.
