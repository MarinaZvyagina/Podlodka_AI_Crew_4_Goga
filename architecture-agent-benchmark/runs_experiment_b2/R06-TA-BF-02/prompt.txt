We've noticed that etcd currently allows creating a user account, or changing an existing
user's password, with a completely blank password — as long as the account isn't explicitly
marked as a no-password (passwordless) account. In practice this means someone can end up with
an account that is supposed to be protected by a password but actually has none, which is a
foot-gun for anyone managing cluster credentials.

Please make user creation and password-change requests reject an empty password, unless the
caller has explicitly opted that account into no-password (passwordless) mode. The error
returned to the client should clearly indicate that the password is missing/invalid, distinct
from other existing authentication errors (e.g. "user not found", "user already exists").

Requirements:
- Creating a new user with a blank password, when the request does not explicitly ask for a
  passwordless account, must fail with a clear error instead of silently succeeding.
- Changing an existing user's password to a blank value must be rejected the same way, unless
  that account is a passwordless account.
- Accounts that are intentionally created as passwordless must keep working exactly as before —
  don't touch that path.
- The check must apply no matter which client or tool is used to talk to the cluster (not just
  one particular CLI or SDK).
