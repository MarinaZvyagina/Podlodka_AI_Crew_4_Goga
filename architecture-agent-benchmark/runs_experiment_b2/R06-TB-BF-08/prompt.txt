Some teams running etcd have run into trouble where a single lease ends up with an enormous
number of keys attached to it — sometimes hundreds of thousands. When that lease later expires
or is revoked, cleaning up all of those keys at once creates a large burst of load on the
cluster, and while that cleanup is happening, other operations involving that lease slow down
noticeably.

We'd like to put a cap on how many keys can be attached to a single lease at a time. This limit
should be configurable when starting an etcd server (with a sensible built-in default that
doesn't break existing deployments). Once a lease has reached the limit, a write that would
attach one more *new* key to that lease should fail with a clear, client-facing error — it must
not silently succeed, must not apply only part of the request, and must not bring the server
down. Writes that don't push a lease over the limit — including a write that re-attaches a key
that is already on that lease — must keep working exactly as they do today.

Requirements:
- Add a configurable maximum number of keys that can be attached to one lease at a time.
- When a write would exceed that limit for the target lease, the request must fail with a clean,
  understandable error returned to the caller.
- The etcd server process must remain healthy and continue serving other requests after such a
  rejection — no crash, no hang, no corrupted state.
- A write that re-attaches a key already on the lease (i.e. doesn't increase the distinct key
  count) must not be rejected.
- Leases under the limit must behave exactly as before.
