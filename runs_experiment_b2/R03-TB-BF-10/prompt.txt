We run several services built on this framework that use WebSocket gateways for real-time
features, and we deploy them behind an orchestrator (Kubernetes) that sends a termination signal
to each instance before killing it, giving the process a short grace period to shut down
cleanly. We already rely on the framework's built-in graceful-shutdown support for the rest of
the app (in-flight HTTP requests finish, cleanup hooks run, etc.), so this is now the expected
way our services wind down.

The gap is real-time clients: when an instance is asked to terminate, any WebSocket clients still
connected just get dropped with no warning, indistinguishable on the client side from a network
failure or a crash. This makes reconnect logic on the frontend unnecessarily defensive and noisy
(retry-with-backoff kicking in for what is really just a normal deploy). We'd like connected
clients to instead get a small heads-up message telling them the server is going away, sent
immediately before their connection is actually closed, as part of that same shutdown sequence we
already trigger — not something a developer has to remember to wire up separately for every
gateway they write.

We use both of the WebSocket integrations this framework ships across different services (one
built on socket.io, one built on the lighter-weight `ws` library), so whatever you build needs to
behave the same way regardless of which one a given service uses. It should also be safe by
default — gateways that don't happen to have any connected clients at shutdown time, or apps that
don't use WebSockets at all, shouldn't see any change in behavior, and normal (non-shutdown)
connect/disconnect/message handling must keep working exactly as before.
